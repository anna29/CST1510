Part 1

What is a SQL database, and why are we using one?

Official docs: Python sqlite3 docs

Before writing any Python, it helps to answer the basic "what?" questions first.

What is a database?

A database is a system for storing and organising data so that the data can be added, searched, updated, and deleted reliably.

What is SQL?

SQL stands for Structured Query Language. It is the language used to describe what should happen to the data in a relational database. For example, SQL can create a table, insert a row, search for matching records, or update an existing value.

What is SQLite?

SQLite is a lightweight relational database system that stores the whole database in a single file. That makes it a very good choice for first-year projects because it is easy to run locally and Python supports it directly through the built-in sqlite3 module.

Why are we moving from files to a database?

Up to Week 9, the module has already used storage, but that storage was still quite fragile. A plain text file is easy to start with, but it does not protect structure for us. We have to remember the order of fields, split lines carefully, and hope every line follows the same pattern.

A database solves a different problem from a normal file:

Plain file Database
stores raw text stores structured records
we decide how to parse every line the table shape is defined once in the schema
easy to break by hand harder to corrupt by accident
awkward to search and filter built for searching and filtering
good for starting better for growing a real application

For this module, the key idea is:

Week 10 upgrades the STORE box from "save some text" to "store structured records that Python can query safely".

How does this fit into your Python program?

Python runs the application logic, but SQL handles the data operations. In practice that means:

  • Python decides when to connect and which values to send.
  • SQL says what table to create, read, update, or delete.
  • SQLite stores the data in a structured database file.

This also prepares the module for the next steps:

  • Week 11 needs data that a user interface can query cleanly.
  • Week 12 benefits from having a proper place to keep app data and users.

So the purpose of SQL this week is not to learn isolated commands. It is to make the project's storage layer behave like a real application.

Part 2

Core SQL vocabulary: table, row, column, schema

Official docs: SQLite SQL language · Python sqlite3 docs

Before looking at Python code, you need a clear picture of what a relational database is storing.

Word Meaning
table one organised set of related data
row one record in that table
column one field repeated for every record
schema the design of the table: column names, types, and rules 
devices
+----+----------+--------------+--------+
| id | name     | ip           | active |
+----+----------+--------------+--------+
| 1  | AP-Lobby | 10.0.0.10    | 1      |
| 2  | Switch-1 | 10.0.0.11    | 0      |
+----+----------+--------------+--------+

In that picture:

  • devices is the table
  • id, name, ip, and active are the columns
  • each horizontal entry is a row
  • the decision that id exists, that name is text, and that active is a number is part of the schema

SQL is the language used to talk to that table. Python is the program that sends SQL instructions to SQLite and receives the answers back.

For first-year work, it helps to separate those two layers explicitly:

  • SQL layer: "what do I want the database to do?"
  • Python layer: "when do I connect, send the query, and use the result?"

That is why a query like this should be read almost as an instruction sentence:

SELECT name, ip
FROM devices
WHERE active = 1;

It means: "from the devices table, give me the name and ip columns, but only for rows where active is 1."

Part 3

Creating a table: defining structure before data

Official docs: Python sqlite3 docs · SQLite CREATE TABLE

The first SQL job is usually not reading data. It is defining the table itself.

CREATE TABLE IF NOT EXISTS devices (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    ip TEXT NOT NULL,
    active INTEGER NOT NULL
);

This statement matters because it fixes the shape of the data before rows are added.

Read it in pieces:

  1. CREATE TABLE means "make a new table".
  2. IF NOT EXISTS prevents the program crashing if the table is already there.
  3. id INTEGER PRIMARY KEY creates a unique identifier for each row.
  4. TEXT NOT NULL means the column stores text and should not be empty.
  5. The schema acts like a contract for every row added later.

The Python around it is straightforward:

with sqlite3.connect("ops.db") as conn:
    cursor = conn.cursor()
    cursor.execute(
        "CREATE TABLE IF NOT EXISTS devices ("
        "id INTEGER PRIMARY KEY, "
        "name TEXT NOT NULL, "
        "ip TEXT NOT NULL, "
        "active INTEGER NOT NULL)"
    )

This is where W10T01_walkthrough.ipynb fits. The notebook gives the live coding context, but the teaching point is this:

  • we create structure first
  • we then trust that structure every time we insert or query

That is a big step up from plain files, where structure is only implied.

Part 4

Connecting Python to SQLite with `sqlite3`

Official docs: Python sqlite3 docs

Python's built-in sqlite3 module is the bridge between a Python script and the database file.

import sqlite3

conn = sqlite3.connect("ops.db")
cursor = conn.cursor()
cursor.execute("SELECT name FROM devices")
rows = cursor.fetchall()
conn.close()

Each line has a job:

Python code Meaning
sqlite3.connect("ops.db") open the database file, or create it if it does not exist
conn.cursor() create an object that sends SQL commands
cursor.execute(...) run one SQL statement
fetchone() / fetchall() get rows back into Python
conn.close() close the connection

For teaching, it helps to stress that SQLite itself is not "inside" Python. Python is talking to another system through the sqlite3 library.

In practice, you should soon move to the safer pattern:

with sqlite3.connect("ops.db") as conn:
    cursor = conn.cursor()
    cursor.execute("SELECT name FROM devices")
    rows = cursor.fetchall()

The with block helps because the connection is cleaned up automatically. It is also a gentler path toward good habits than asking first-years to remember every manual close and commit.

Part 5

Adding and reading data: `INSERT`, `SELECT`, and placeholders

Official docs: Python sqlite3 docs · SQLite SELECT

Once the table exists, there are two core moves:

  • put rows in
  • read rows back out

Adding a row

cursor.execute(
    "INSERT INTO devices (name, ip, active) VALUES (?, ?, ?)",
    ("AP-Lobby", "10.0.0.10", 1),
)

The SQL text contains ? placeholders. The second argument provides the real values.

That separation is extremely important:

  • the SQL statement describes the structure of the command
  • the tuple supplies the data values

Reading rows back

cursor.execute(
    "SELECT name, ip FROM devices WHERE active = ?",
    (1,),
)
rows = cursor.fetchall()

Two details matter here:

  1. (1,) is a one-item tuple. The comma matters.
  2. fetchall() returns the query result back into Python, usually as a list of tuples.

The SQL itself is also worth reading line by line:

SELECT name, ip
FROM devices
WHERE active = 1;
  • SELECT chooses columns
  • FROM names the table
  • WHERE filters rows

This part aligns closely with W10T02_walkthrough.ipynb. The notebook can show several variations, but the core teaching pattern should stay steady.

Part 6

Why placeholders matter: safe SQL and SQL injection

Official docs: Python sqlite3 docs

By Week 10, you already know f-strings, which means it is tempting to build SQL with string formatting. This is the right point to see why that becomes a bad habit.

Unsafe style:

username = input("Username: ")
query = f"SELECT * FROM users WHERE username = '{username}'"
cursor.execute(query)

Safer style:

username = input("Username: ")
cursor.execute(
    "SELECT * FROM users WHERE username = ?",
    (username,),
)

The second version is better because the data value is passed separately from the SQL command text. That makes the query safer and easier to reason about.

For a first-year audience, the main lesson does not need to become a full security lecture. The important message is:

SQL text should stay SQL text. User data should stay data.

That sentence is short enough to teach, remember, and reuse later in web and AI contexts too.

Part 7

Changing existing data: `UPDATE`, `DELETE`, and `WHERE`

Official docs: SQLite UPDATE · SQLite DELETE

Creating and reading are only part of storage. A useful application must also change and remove records.

Imagine the table currently contains:

+----+-----------+--------------+--------+
| id | name      | ip           | active |
+----+-----------+--------------+--------+
| 1  | AP-Lobby  | 10.0.0.10    | 1      |
| 2  | Switch-1  | 10.0.0.11    | 1      |
| 3  | Old-Switch| 10.0.0.99    | 0      |
+----+-----------+--------------+--------+

UPDATE

UPDATE devices
SET active = 0
WHERE name = 'AP-Lobby';

Question: after this query runs, which rows change?

Answer: only the row where name = 'AP-Lobby' changes. Its active value becomes 0. The other rows are untouched.

After the query:

+----+-----------+--------------+--------+
| id | name      | ip           | active |
+----+-----------+--------------+--------+
| 1  | AP-Lobby  | 10.0.0.10    | 0      |
| 2  | Switch-1  | 10.0.0.11    | 1      |
| 3  | Old-Switch| 10.0.0.99    | 0      |
+----+-----------+--------------+--------+

DELETE

DELETE FROM devices
WHERE name = 'Old-Switch';

Question: what is left in the table after this query runs?

Answer: the row for Old-Switch is removed. The remaining rows stay exactly as they were.

After the query:

+----+----------+--------------+--------+
| id | name     | ip           | active |
+----+----------+--------------+--------+
| 1  | AP-Lobby | 10.0.0.10    | 0      |
| 2  | Switch-1 | 10.0.0.11    | 1      |
+----+----------+--------------+--------+

The dangerous idea here is forgetting the WHERE clause.

UPDATE devices
SET active = 0;

Question: what happens now?

Answer: every row in devices is updated, because there is no filter telling SQLite which rows to target.

That is why WHERE matters so much:

  • with WHERE, the change is targeted
  • without WHERE, the change may affect the whole table

The Python wrapper is the same pattern as before:

cursor.execute(
    "UPDATE devices SET active = ? WHERE name = ?",
    (0, "AP-Lobby"),
)

So although the SQL verbs change, the safe Python structure stays consistent. That consistency is what helps the week feel manageable.

Part 8

Transactions, commit, and the `with` pattern

Official docs: Python sqlite3 docs

Many beginner database bugs are not SQL bugs at all. They come from forgetting that changes are part of a transaction.

In a manual pattern:

conn = sqlite3.connect("ops.db")
cursor = conn.cursor()
cursor.execute(
    "INSERT INTO devices (name, ip, active) VALUES (?, ?, ?)",
    ("FW-Edge", "10.0.0.1", 1),
)
conn.commit()
conn.close()

If commit() is forgotten, the change may not be saved.

That is why you should quickly move to this safer pattern:

with sqlite3.connect("ops.db") as conn:
    cursor = conn.cursor()
    cursor.execute(
        "INSERT INTO devices (name, ip, active) VALUES (?, ?, ?)",
        ("FW-Edge", "10.0.0.1", 1),
    )

The with pattern is worth teaching as a habit, not just a convenience:

  • it reduces boilerplate
  • it makes code easier to read
  • it lowers the chance of forgetting a key step
  • it fits nicely with the idea of safe resource handling
Part 9

Notebook map and quick recap

By the end of Week 10, you should be able to recognise and use these core ideas:

  • a database stores structured records in tables
  • SQL tells the database what to do
  • Python uses sqlite3 to send SQL and receive results
  • placeholders keep data separate from SQL text
  • WHERE controls which rows are affected
  • the with pattern is the safer way to manage the connection

One useful summary is:

with sqlite3.connect("ops.db") as conn:
    cursor = conn.cursor()
    cursor.execute(
        "SELECT name, ip FROM devices WHERE active = ?",
        (1,),
    )
    rows = cursor.fetchall()

That short example captures most of the week:

  • open the database
  • run SQL safely
  • filter rows
  • fetch the result back into Python

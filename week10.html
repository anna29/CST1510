Primer

Before Topic 1 — What SQL Is

Official docs: SQLite SQL language · Python sqlite3 docs

SQL is the language we use to talk to a relational database. Python is not replacing SQL this week; Python is simply the program that sends SQL commands to SQLite and receives the results back.

Think of the database as a set of tables:

Word Meaning
table a whole grid of related data
row one record in that table
column one field repeated for every row 
devices
+----+----------+--------------+--------+
| id | name     | ip           | active |
+----+----------+--------------+--------+
| 1  | AP-Lobby | 10.0.0.10    | 1      |
| 2  | Switch-1 | 10.0.0.11    | 0      |
+----+----------+--------------+--------+
   row 1         row 2

columns: id, name, ip, active

The four SQL jobs students meet first are:

SQL verb What it does
CREATE TABLE define the shape of the table
INSERT INTO add rows
SELECT read rows back out
UPDATE / DELETE change or remove existing rows

Read a query almost like an instruction sentence:

SELECT name, ip
FROM devices
WHERE active = 1;

This means: "from the devices table, give me the name and ip columns, but only for rows where active is 1."

A few beginner-friendly rules help here:

  • SQL keywords are often written in capitals for readability, but SQL itself is not demanding capitals.
  • The semicolon marks the end of a statement. In Python strings, it is often optional for SQLite, but it is still a good habit when learning SQL.
  • SELECT * means "all columns", but naming the columns you actually want is usually clearer.
  • The WHERE part filters rows. If there is no WHERE, the command affects or returns all rows.

Once that picture is clear, the Python code in this week makes more sense: sqlite3.connect(...) opens the database file, cursor.execute(...) sends SQL to it, and methods like fetchone() or fetchall() bring the answers back into Python.

Connecting and Creating Tables

The whole database is one file. No server, nothing to install — import sqlite3 is already in Python.

2.CREATE TABLE — defining the shape

IF NOT EXISTS avoids an error if it is already there. PRIMARY KEY is a unique, auto-numbered row identifier.

cursor.execute("""
    CREATE TABLE IF NOT EXISTS devices (
        id     INTEGER PRIMARY KEY,
        name   TEXT NOT NULL,
        ip     TEXT UNIQUE NOT NULL,
        active INTEGER DEFAULT 1
    )
""")
conn.commit()
Practice

Create a table called notes with id (primary key) and text (not null).

3.Five storage classes — that is genuinely all of them

INTEGER, REAL, TEXT, BLOB, NULL. No separate date type — store dates as TEXT, ISO format (YYYY-MM-DD), so they still sort correctly.

cursor.execute("""
    CREATE TABLE readings (
        id       INTEGER PRIMARY KEY,
        sensor   TEXT NOT NULL,
        value    REAL NOT NULL,
        recorded TEXT NOT NULL
    )
""")
conn.commit()
Practice

Design a CREATE TABLE statement for log entries: id, timestamp (TEXT), level (TEXT), message (TEXT).

4.SQLite will not stop you being wrong

It is flexible about types — a string can land in a REAL column with no error at all. Your own code has to enforce what the schema will not.

cursor.execute("INSERT INTO readings (sensor, value, recorded) VALUES (?, ?, ?)",
               ("temp-01", "not-a-number", "2026-09-08"))
conn.commit()

row = cursor.execute("SELECT value FROM readings").fetchone()
print(row, type(row[0]))    # stored as-is - no error, no warning
Practice

Write a small function that converts a value to float before inserting it, so a bad value fails loudly instead of being stored silently.

Same idea, three fields

Field Looks like

Common mistakes

Mistake What you see Fix
forgetting conn.commit() changes silently vanish commit after every write, or use with (Topic 3)
assuming a type is enforced a string lands in a REAL column with no error validate/convert in Python before inserting
querying a table that does not exist yet sqlite3.OperationalError: no such table run CREATE TABLE first, check the name matches exactly
forgetting NOT NULL/UNIQUE where it matters duplicate or missing data slips in silently decide your constraints when you design the schema, not after

Topic 2

Inserting and Querying

Adding rows, getting them back, and the one habit that keeps you safe from SQL injection.

Already know this? Skip to the Topic 2 Challenge.

Official docs: Python sqlite3 docs · SQLite SELECT

1.? placeholders — never build SQL by joining strings

cursor.execute(
    "INSERT INTO devices (name, ip, type) VALUES (?, ?, ?)",
    ("Router-A", "10.0.0.1", "router"),
)
conn.commit()
Practice

Insert a device of your own using a placeholder query.

2.executemany() — several rows at once

rows = [("Switch-1", "10.0.0.2", "switch"), ("AP-Lobby", "10.0.0.3", "access point")]
cursor.executemany("INSERT INTO devices (name, ip, type) VALUES (?, ?, ?)", rows)
conn.commit()
Practice

Use executemany() to insert 3 rows of your own choosing.

3.fetchall(), fetchone(), and iterating the cursor directly

print(cursor.execute("SELECT * FROM devices").fetchall())
print(cursor.execute("SELECT name FROM devices WHERE id = ?", (999,)).fetchone())   # None, no crash

for name, ip in cursor.execute("SELECT name, ip FROM devices"):
    print(name, "->", ip)
Practice

SELECT a row you know does not exist and confirm fetchone() gives None, not an error.

4.SQL injection — seeing it actually work, and actually get blocked

Building SQL by joining a string in is not a style choice — it is a real vulnerability.

name = "' OR '1'='1"
unsafe = f"SELECT * FROM devices WHERE name = '{name}'"
print(cursor.execute(unsafe).fetchall())    # returns EVERY row - the WHERE did nothing

safe = cursor.execute("SELECT * FROM devices WHERE name = ?", (name,)).fetchall()
print(safe)    # empty - treated as data, not code
Practice

Try your own malicious-looking string against both the unsafe and safe versions and compare the results.

Challenge

Insert 4 devices of different types. Then write one query using WHERE, ORDER BY and LIMIT together to find the 2 most recently inserted routers.

Same idea, three fields

Field Looks like
AI / Data Science inserting cleaned rows from a DataFrame, one at a time or via to_sql()
Cyber Security querying incidents WHERE severity = ? safely, even with attacker-controlled input
IT filtering devices WHERE type = ? AND active = 1

Common mistakes

Mistake What you see Fix
building SQL with an f-string and a real value SQL injection — a crafted value can return or destroy data it should not always use ? placeholders
forgetting the trailing comma on a single value ProgrammingError: Incorrect number of bindings supplied (value,) is a tuple; (value) is not
expecting fetchone() to error when nothing matches it returns None quietly check for None before using the result
mixing up fetchall() and iterating the cursor both work, but calling fetchall() twice returns nothing the second time fetch once, store the result if you need it twice

Topic 3

Updating, Deleting and the Safe Pattern

The one mistake in this topic affects every row in a table at once — worth slowing down for.

Already know this? Skip to the Topic 3 Challenge.

Official docs: Python sqlite3 docs · SQLite UPDATE · SQLite DELETE

1.UPDATE — changing existing rows

cursor.execute("UPDATE devices SET ip = ? WHERE id = ?", ("10.0.0.254", 1))
conn.commit()
print(cursor.execute("SELECT name, ip FROM devices WHERE id = 1").fetchone())
Practice

Update one device's name, then confirm the change with a SELECT.

2.rowcount — how many rows actually changed

result = cursor.execute("UPDATE devices SET active = 0 WHERE name = ?", ("AP-Lobby",))
conn.commit()
print(result.rowcount)
Practice

Update a row and print how many rows rowcount says were affected.

3.DELETE, and the mistake that affects every row

A missing WHERE on UPDATE or DELETE changes or removes everything in the table — no confirmation, no undo.

cursor.execute("DELETE FROM devices WHERE active = 0")
conn.commit()
print(cursor.execute("SELECT name FROM devices").fetchall())

# cursor.execute("DELETE FROM devices")
# -> wipes the WHOLE table. Always run the matching SELECT first.
Practice

Run the matching SELECT for a DELETE you are about to write, and check the result looks right, before actually deleting.

4.The with pattern — commit and close, handled for you

Auto-commits on success. Auto-rolls-back if an error is raised inside the block — nothing half-finished gets saved.

try:
    with sqlite3.connect("network.db") as c:
        c.execute("INSERT INTO devices (name, ip) VALUES (?, ?)", ("Duplicate", "10.0.0.254"))
except sqlite3.IntegrityError as e:
    print("Nothing was committed:", e)
Practice

Rewrite one of Topic 2's inserts to use the with pattern instead of a manual commit().

Challenge

Using with, insert a device, then trigger a UNIQUE constraint violation on purpose inside a second with block, and confirm the first insert is still there afterwards but the second never landed.

Same idea, three fields

Field Looks like
AI / Data Science correcting one bad value in a stored dataset
Cyber Security marking one incident resolved, without touching the others
IT decommissioning one server record, by id, never by a blanket delete

Common mistakes

Mistake What you see Fix
UPDATE/DELETE with no WHERE every row changes or disappears always include WHERE, run the matching SELECT first
forgetting conn.commit() outside a with block the change silently does not persist commit explicitly, or switch to with
leaving a connection open resources leak in a long-running program close it, or use with so it happens automatically
assuming rowcount means something before commit() it is still accurate — the mistake is elsewhere, usually a missing commit after check commit happened, not just rowcount

Topic 4

Migrating Real Data In

Three weeks of separate skills — Week 7's parsing, Week 8's pulled data, Week 9's flat-file users — converging into one real database.

Already know this? Skip to the Topic 4 Challenge.

Official docs: DataFrame.to_sql · pandas.read_sql

1.DataFrame.to_sql() — the whole migration, one line

import pandas as pd, requests
from io import StringIO

url = "https://raw.githubusercontent.com/mwaskom/seaborn-data/master/tips.csv"
df = pd.read_csv(StringIO(requests.get(url, timeout=10).text))

with sqlite3.connect("network.db") as conn:
    df.to_sql("tips", conn, if_exists="replace", index=False)
print("migrated", len(df), "rows")

3.Migrating Week 9's flat file into a users table

Week 7's parsing pattern, applied to a security-relevant file, landing in a real table.

with sqlite3.connect("network.db") as conn:
    conn.execute("""CREATE TABLE IF NOT EXISTS users (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        username TEXT NOT NULL UNIQUE,
        password_hash TEXT NOT NULL
    )""")
    with open("users.txt") as f:
        for line in f:
            username, password_hash = line.strip().split(",", 1)
            conn.execute(
                "INSERT OR IGNORE INTO users (username, password_hash) VALUES (?, ?)",
                (username, password_hash),
            )
Practice

Explain, in one sentence, what INSERT OR IGNORE does differently from a plain INSERT here, and why it matters if you run the migration twice.

4.Login still works exactly the same way

checkpw() does not care whether the hash came from a file or a database row — Week 9's logic did not need to change at all, only where it reads from.

import bcrypt

with sqlite3.connect("network.db") as conn:
    stored = conn.execute(
        "SELECT password_hash FROM users WHERE username = ?", ("alice",)
    ).fetchone()

if stored:
    print(bcrypt.checkpw(b"correct-horse-battery-staple", stored[0].encode("utf-8")))

Common mistakes

Mistake What you see Fix
running the migration twice without OR IGNORE/a UNIQUE check IntegrityError, or silent duplicates design for "may run again" from the start
forgetting if_exists="replace" (or "append") on to_sql() ValueError: Table already exists on a second run choose deliberately, do not just guess
deleting the old flat file before confirming the migration worked data loss if the migration had a bug verify from the database first, delete the source second
forgetting the .db file needs to go in .gitignore real hashed passwords committed to your repository add it before the first commit that includes it

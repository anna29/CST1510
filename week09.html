Topic 1

Why Hash, Not Encrypt

Before any bcrypt function, the concept: what hashing actually is, and why it is the right tool for a password.

Already know this? Skip to the Topic 1 Challenge.

Official docs: hashlib

1.Hashing is one-way, deterministic, and a fixed size

Same input, same output, always — and no function reverses it back.

import hashlib

print(hashlib.sha256(b"password123").hexdigest())
print(hashlib.sha256(b"password123").hexdigest())   # identical, every time
Practice

Hash your own name with hashlib.sha256 and confirm hashing it twice gives the same result.

2.The avalanche effect

One character different in the input changes the entire output — there is no "close" match to look for.

print(hashlib.sha256(b"password123").hexdigest())
print(hashlib.sha256(b"password124").hexdigest())
Practice

Change one character in a string of your own and compare the two hashes.

3.Why not encryption?

Encryption is two-way — whoever holds the key can decrypt it back. A password only ever needs checking, never recovering, so a one-way hash is the safer tool: there is no key to steal.

typed = "password123"
stored_hash = hashlib.sha256(b"password123").hexdigest()

# verify by hashing AGAIN and comparing - never by decrypting
print(hashlib.sha256(typed.encode()).hexdigest() == stored_hash)
Practice

Explain, in your own words, why "hash again and compare" replaces "decrypt and compare" for a password.

4.Rainbow tables, and why salting defeats them

An attacker can pre-compute hashes for millions of common passwords once, then just look up a stolen hash in that table. A unique random salt per user makes every hash different, even for the same password — the table becomes useless.

common = ["123456", "password", "qwerty"]
table = {hashlib.sha256(p.encode()).hexdigest(): p for p in common}

stolen = hashlib.sha256(b"qwerty").hexdigest()
print(stolen in table)     # True - instantly cracked, no salt
Practice

Add "letmein" to common and check whether a stolen hash of it would be found in the table.

Challenge

Given a small rainbow table (5 common passwords) and a "stolen" hash of a genuinely random, unique password, show it is not found in the table — then explain in one sentence why length and randomness matter more than any particular character rule.

Topic 2

bcrypt in Python

Two functions, and the one design choice worth understanding: bcrypt is slow on purpose.

Already know this? Skip to the Topic 2 Challenge.

Official docs: bcrypt on PyPI

1.bcrypt works with bytes — encode first

import bcrypt

password = "correct-horse-battery-staple"
password_bytes = password.encode("utf-8")
Practice

Encode a password of your own choosing to bytes.

2.gensalt() + hashpw() — generating a hash

The salt is generated fresh, at random, and embedded inside the hash itself — you never store it separately.

salt = bcrypt.gensalt()
hashed = bcrypt.hashpw(password_bytes, salt)
print(hashed.decode("utf-8"))
print(len(hashed))    # always 60 characters
Practice

Hash your own encoded password from section 1 and print the result.

3.checkpw() — verifying, without ever decrypting

Re-derives the salt from the stored hash, re-hashes the candidate, and compares.

print(bcrypt.checkpw(b"correct-horse-battery-staple", hashed))    # True
print(bcrypt.checkpw(b"wrong-password", hashed))                     # False
Practice

Check your own hash from section 2 against the right password, then a wrong one.

4.The cost factor — slow is the feature

Each +1 roughly doubles the work. A fraction of a second for a real login; days added up across a brute-force attempt.

import time

for rounds in (10, 12, 14):
    start = time.perf_counter()
    bcrypt.hashpw(password_bytes, bcrypt.gensalt(rounds=rounds))
    print(rounds, f"{time.perf_counter() - start:.3f}s")
Practice

Time cost factor 8 alongside 10, 12 and 14. How much faster is it?

Challenge

Write generate_hash(password) and is_valid_hash(password, hashed) — the two functions this whole week's project rests on. Test both with a right and a wrong password.

Same idea, three fields

Field Looks like

Common mistakes

Mistake What you see Fix
passing a str instead of bytes TypeError: argument 'password': 'str' object cannot be converted to 'PyBytes' .encode("utf-8") first
swapping the argument order in checkpw() ValueError: Invalid salt password first, hash second — always
storing the salt separately from the hash unnecessary — and easy to lose track of which belongs to which bcrypt already embeds it in the hash string
picking an unnecessarily high cost factor logins become slow for everyone, including real users the default is already a reasonable choice

Topic 3

Register and Login

Wiring bcrypt into a real, if simple, authentication flow against a file.

Already know this? Skip to the Topic 3 Challenge.

Official docs: bcrypt on PyPI · Reading and writing files

1.Registering — hash, then append

import bcrypt

def register_user(username, password, path="users.txt"):
    """Hash password and append username,hash to the store."""
    hashed = bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt())
    with open(path, "a") as f:
        f.write(f"{username},{hashed.decode('utf-8')}\n")

register_user("alice", "correct-horse-battery-staple", "demo.txt")
with open("demo.txt") as f:
    print(f.read())
Practice

Register a second user into the same file and print the file's contents.

2.Logging in — find the line, then checkpw()

Week 7's .strip().split(",", 1) pattern, applied to a security-relevant file.

def login_user(username, password, path="users.txt"):
    """Return True if username/password match a stored, hashed record."""
    with open(path) as f:
        for line in f:
            stored_username, stored_hash = line.strip().split(",", 1)
            if stored_username == username:
                return bcrypt.checkpw(password.encode("utf-8"), stored_hash.encode("utf-8"))
    return False

print(login_user("alice", "correct-horse-battery-staple", "demo.txt"))
print(login_user("alice", "wrong-guess", "demo.txt"))
Practice

Log in with a username that was never registered, and confirm it returns False without crashing.

3.A missing file should not crash a login attempt

The first person to ever try logging in will hit a file that does not exist yet — handle it, do not let it crash.

import os

def login_user_safe(username, password, path="users.txt"):
    """Return False, not a crash, if the store does not exist yet."""
    if not os.path.exists(path):
        return False
    return login_user(username, password, path)

print(login_user_safe("nobody", "anything", "does_not_exist.txt"))
Practice

Call login_user_safe on a path you know does not exist and confirm it returns False cleanly.

4.Refusing a duplicate username

Registering the same username twice silently creates two records — the login() function only ever finds the first. Worth refusing outright.

def username_exists(username, path="users.txt"):
    """Return True if username already has a record in the store."""
    if not os.path.exists(path):
        return False
    with open(path) as f:
        for line in f:
            stored_username, _ = line.strip().split(",", 1)
            if stored_username == username:
                return True
    return False
Practice

Use username_exists inside register_user to refuse a duplicate registration, returning False instead of writing a second line.

Topic 4

Keeping Secrets Out of Code

Hashing protects passwords. This topic protects everything else — API keys, tokens, anything that must never sit in a file you might commit.

Already know this? Skip to the Topic 4 Challenge.

Official docs: os.environ

1.A hard-coded secret is a mistake, not a style issue

The moment it is pushed to a public repository, it is compromised — deleting it later does not help, it is still in the commit history.

# BAD - never do this:
# API_KEY = "sk-abc123realsecretvalue"

print("see the comment above - nothing to run here")
Practice

Explain in one sentence why deleting a leaked key from your latest commit does not fix the leak.

2.Environment variables — the secret lives outside your code

import os

api_key = os.environ.get("MY_API_KEY", "not set")
print(api_key)
Practice

Set an environment variable in your terminal, then read it back with os.environ.get().

A default like "not set" is fine for something optional. When a variable is required — the program genuinely cannot continue without it — raise a clear error instead of letting it fail later with a confusing message.

def require_env(name):
    """Return the named environment variable, or raise a clear error if it is missing."""
    value = os.environ.get(name)
    if value is None:
        raise RuntimeError(f"{name} is not set. Set it before running this.")
    return value

try:
    require_env("MY_API_KEY")
except RuntimeError as e:
    print("Caught it:", e)
Practice

Write require_env("HOME") (or another variable you know is set on your machine) and check it returns the value instead of raising.

3..gitignore — deciding what never gets tracked

Once your project has real accounts and real keys, these need to be in it.

gitignore_lines = ["*.db", "*.env", ".streamlit/secrets.toml", "__pycache__/", "users.txt"]
for line in gitignore_lines:
    print(line)

4.If a secret leaks anyway

Removing it from the latest commit is not enough — it is still readable in history. Revoke the key at its source first, generate a new one, worry about cleaning history second.

Common mistakes

Mistake What you see Fix
committing a .db or .txt file full of real hashed users it is now in your repository's history add it to .gitignore before the first commit that includes it
assuming a private repo makes secrets safe tutors, group members, and future public forks can still see it treat every repo as if it could become public
hard-coding "just for testing" it is easy to forget to remove before committing use an environment variable from the start, even in testing
checking .gitignore after committing the file once too late — it is already tracked git rm --cached <file> is needed on top of .gitignore if this happens
defaulting a required variable to "not set" and carrying on it fails later, somewhere confusing, instead of here raise a clear error the moment you know it's missing

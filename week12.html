Part 1

API Keys, Reviewed

Official docs: os.environ · OpenAI quickstart

Week 9's lesson, one more time, for the one secret this whole week revolves around — and the pattern that makes a feature genuinely optional.

Before you start — where OPENAI_API_KEY comes from

If you want to try the optional AI feature for real, you first need your own OpenAI API key.

  1. Sign in to the OpenAI platform dashboard.
  2. Create an API key there.
  3. Copy it once and store it safely — treat it like a password.
  4. Set it as an environment variable in your terminal.

macOS / Linux

export OPENAI_API_KEY="your_api_key_here"

Windows PowerShell

$env:OPENAI_API_KEY="your_api_key_here"

OpenAI's Python tools can read the key from the environment automatically.

If you do not have a key, keep going anyway: the AI feature is optional this week, and the required part of the coursework must still work without it.

Docs: OpenAI quickstart

1.Loading the key — the same habit as Week 9

import os

api_key = os.environ.get("OPENAI_API_KEY")
print("set" if api_key else "not set")

2.Two different responses to a missing key

Sometimes you want a clear, loud error. Sometimes you want the feature to just quietly not appear. Both are correct — depending on what the feature is.

def require_key():
    """Raise a clear error if the key is missing - use when the feature MUST have it."""
    key = os.environ.get("OPENAI_API_KEY")
    if key is None:
        raise RuntimeError("OPENAI_API_KEY is not set.")
    return key

def optional_key():
    """Return None if missing - use when the feature can just be skipped."""
    return os.environ.get("OPENAI_API_KEY")

3.Making a feature optional, end to end

The required part of the app never depends on the optional part succeeding.

def get_ai_summary(text):
    """Return a summary, or None if no key is set - never crashes."""
    api_key = os.environ.get("OPENAI_API_KEY")
    if api_key is None:
        return None
    return f"(a real summary would go here for: {text[:20]}...)"

def render_report(records):
    print(f"Checked {len(records)} records.")
    summary = get_ai_summary(str(records))
    print(summary if summary else "(AI summary skipped - no key set)")

render_report(["srv-01: OK", "srv-02: OVER LIMIT"])

Same idea, three fields

Field Looks like
AI / Data Science an optional AI-generated dataset summary, dashboard works without it
Cyber Security an optional AI incident triage note, alerts still work without it
IT an optional AI-suggested fix, the status page works without it

Common mistakes

Mistake What you see Fix
hard-coding a key "just to test" it is one commit away from a public leak os.environ.get(), from the first line you write
letting a missing key crash the whole app the required features become unavailable too check for the key, degrade only the optional part
printing the key anywhere, even partially, to debug it is now in your terminal history or logs print "set"/"not set", never the value
forgetting the difference between require_key() and optional_key() either an unwanted crash, or a silent missing feature nobody notices choose deliberately per feature

2.The reply's exact shape

response.choices[0].message.content — this path is the same every time, worth knowing by heart rather than looking up each time.

3.The API is stateless — history has to be resent every time

Nothing is remembered between calls unless YOU send the whole conversation back.

messages = [{"role": "system", "content": "You are a concise ops assistant."}]

def ask(client, user_text):
    messages.append({"role": "user", "content": user_text})
    response = client.chat.completions.create(model="gpt-4o-mini", messages=messages)
    reply = response.choices[0].message.content
    messages.append({"role": "assistant", "content": reply})   # <- this line IS the memory
    return reply

4.Verifying the calling code without a real key — mocking, previewed

Topic 3 teaches this properly. Here is the idea: a fake client that behaves like the real one, so you can check YOUR code is right without a network call.

from unittest.mock import MagicMock

fake_client = MagicMock()
fake_client.chat.completions.create.return_value.choices = [
    MagicMock(message=MagicMock(content="4"))
]

reply = ask(fake_client, "what is 2+2?")
print(reply)          # "4" - from the fake, not a real call
print(messages)         # still updated correctly

Part 3

Testing Your App

Official docs: pytest getting started · unittest.mock

The pure-function parts of your project can be tested directly. The parts that touch a network can be tested too — without actually touching it.

1.A pytest test is a function starting with test_

assert checks something is true — if not, the test fails and tells you exactly what happened.

def status_of(open_issues, warning_at=50, limit=100):
    if open_issues >= limit:
        return "OVER LIMIT"
    elif open_issues >= warning_at:
        return "WARNING"
    else:
        return "OK"

def test_status_over_limit():
    assert status_of(150) == "OVER LIMIT"

test_status_over_limit()
print("passed")

2.Test the edges, not just the middle

This is where real bugs hide — the exact boundary between two branches.

def test_status_exactly_at_limit():
    assert status_of(100) == "OVER LIMIT"   # >= , not >

def test_status_just_below_warning():
    assert status_of(49) == "OK"

test_status_exactly_at_limit()
test_status_just_below_warning()
print("both passed")

3.Testing code that calls something external — with a mock

MagicMock stands in for a real client. You decide exactly what it "returns" — no network, no key, no cost, no flakiness.

from unittest.mock import MagicMock

def ask(client, messages, user_text):
    messages.append({"role": "user", "content": user_text})
    response = client.chat.completions.create(model="gpt-4o-mini", messages=messages)
    reply = response.choices[0].message.content
    messages.append({"role": "assistant", "content": reply})
    return reply

def test_ask_returns_mocked_reply():
    client = MagicMock()
    client.chat.completions.create.return_value.choices = [MagicMock(message=MagicMock(content="4"))]
    assert ask(client, [], "2+2?") == "4"

test_ask_returns_mocked_reply()
print("passed, no real API call made")

4.Running with the real pytest command

pytest filename.py finds every test_ function automatically and reports pass/fail for each, with the exact line that failed.

Same idea, three fields

Field Looks like

Cyber Security testing a severity classifier against known edge-case incidents

Common mistakes

Mistake What you see Fix
only testing the "happy path" bugs hide at the exact boundaries test the edges: exactly at each threshold
calling a real, paid API inside a test slow, costs money, fails when the network is down mock the client instead
a test with no assert at all it "passes" without checking anything every test needs at least one real assertion
one giant test checking everything a failure does not tell you which part broke one focused thing per test function

Part 4

Deploying

Official docs: Deploy your app · Requirements file format

The last step. A working app on your machine is not the same thing as a working app someone else can open.

1.requirements.txt — what the cloud needs to install

Without this, the deployed app fails to even start.

REQUIREMENTS = ["streamlit", "pandas", "requests", "bcrypt", "openai"]
for lib in REQUIREMENTS:
    print(lib)

2..gitignore — the last check before every commit from here

GITIGNORE = ["*.db", ".streamlit/secrets.toml", "__pycache__/", ".pytest_cache/"]
for pattern in GITIGNORE:
    print(pattern)

3.A pre-flight check script — catching mistakes before Streamlit Cloud does

import os

def check_requirements_txt(project_dir):
    path = os.path.join(project_dir, "requirements.txt")
    return os.path.exists(path) and os.path.getsize(path) > 0

print(check_requirements_txt("."))

4.The real deployment steps

Push to GitHub → requirements.txt and .gitignore correct → connect the repo on share.streamlit.io → paste secrets into the Cloud dashboard, never into a file → test the public URL in a browser you are not logged into.

Same idea, three fields

Field Looks like
AI / Data Science a dataset console anyone on the team can open and use
Cyber Security an incident console reachable by whoever is on call
IT a status dashboard live for the whole team, not just your laptop

Common mistakes

Mistake What you see Fix
deploying without testing on a fresh clone first it worked locally, fails in the cloud clone into a fresh folder, test from there before deploying
a .db file committed before .gitignore caught it real hashed passwords are now in your public history remove and revoke; .gitignore alone does not fix an already-committed file
secrets pasted into a file instead of the Cloud dashboard leaked the moment the repo is public st.secrets locally, the Cloud Secrets panel once deployed
assuming "it works on my machine" is enough a stranger's fresh clone fails the pre-flight checklist exists exactly for this gap

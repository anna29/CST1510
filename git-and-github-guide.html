Git and GitHub Guide

The weekly routine for saving your work: check what changed, stage it, commit it, push it, then confirm it is really on GitHub.

Your GitHub repository is not just backup. It is part of the evidence that your work was completed week by week across the term. Haven't set it up yet? Do the Setup Guide first.

The short version, once you know the steps:

git status
git add .
git commit -m "Week N lab and mini-project"
git push

Then open GitHub in a browser and check the files are really there.

Step 0. Open a terminal in the right folder

Start here

You need to be inside your CST1510 repository folder, not just somewhere in Documents.

The easiest way: in VS Code, File → Open Folder and choose CST1510, then Terminal → New Terminal. The terminal opens in the right place.

Not sure where you are? Run:

pwd

The path should end in CST1510. If it doesn't, open the folder in VS Code as above.

Step 1. See what changed

Look first 
git status

modified means you changed an existing file. untracked means there is a new file Git has not seen before.

On branch main
Your branch is up to date with 'origin/main'.

Changes not staged for commit:
  modified:   Week 04 - Lists, Dictionaries and Files/LAB/W04_Lab.ipynb
  modified:   Week 04 - Lists, Dictionaries and Files/LAB/template.py

Untracked files:
  Week 04 - Lists, Dictionaries and Files/LAB/my_records.csv

Step 2. Stage everything for the snapshot

Prepare it 
git add .

This usually prints nothing. That is normal. The dot means everything in this repository folder, except anything listed in your .gitignore.

Check again:

git status

Files should now appear under Changes to be committed.

Step 3. Save a local snapshot

Commit it 
git commit -m "Week 4 lab and mini-project"

Change the week number to the week you are on. This saves the snapshot on your computer only.

Step 4. Send it to GitHub

Push it 
git push

The first time, VS Code asks you to sign in to GitHub: click Allow and follow the browser window.

Step 5. Check it really arrived

Verify it

Open your repository on GitHub in a browser and make sure this week's files are visible there.

A successful git push is a good sign, but seeing the files on GitHub is the real check.

What goes in the repository

Put each week's folder from Moodle inside CST1510, but only its LAB folder is uploaded: your lab notebook, your mini-project and the warm-up fixes. The walkthroughs, examples and demo stay on your computer. Your .gitignore does this for you, so git add . is still all you type.

Do your lab work inside the week's LAB folder. Anything saved elsewhere in a week folder won't go to GitHub.

The .gitignore file

You made this once during setup. It sits in the CST1510 folder and lists files Git should never upload. It should contain:

# Learning material: only each week's LAB folder is uploaded
Week */*
!Week */LAB/

# Files that should never be uploaded
.venv/
__pycache__/
.ipynb_checkpoints/
__MACOSX/
.DS_Store
.env
LineWhat it is
Week */* and !Week */LAB/Skip everything inside each week's folder, except the LAB folder. The walkthroughs, examples and demo are learning material, not your work.
.venv/Your virtual environment. It's large and only works on your computer.
__pycache__/Files Python creates automatically when it runs your code.
.ipynb_checkpoints/Autosave copies of Jupyter notebooks.
__MACOSX/A junk folder that appears when a zip made on a Mac is unzipped on Windows.
.DS_StoreA hidden file macOS puts in folders. Nothing to do with your code.
.envWhere passwords and API keys go in later weeks. These must never be uploaded.

If git status ever lists a file you don't recognise, stop and check before you commit.

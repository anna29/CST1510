Week 4 — Lists, Dictionaries and Files

By the end of this week you can create a list, index into it, slice it, and change it in place, loop over a list directly, without counting, and build a new list from an old one in one line, with a list comprehension.

Part 1

Lists

Official docs: More on lists

One variable holds one value. A list holds many, in order.

Resources

Python documentation — Data Structures: Lists, Tuples — the official reference, if you want more than this walkthrough covers.

1.Creating a list, and indexing

Indexing counts from 0 — the same rule as range().

labels = ["R-001", "R-002", "R-003"]

print(labels[0])
print(labels[1])
print(labels[2])
index:     0        1        2
labels:  ["R-001", "R-002", "R-003"]
            ▲                  ▲
        labels[0]          labels[-1]

Animation — Indices and Slices — open this on the main screen to walk through indexing and slicing interactively.

2.Negative indexing

Counts from the end. labels[-1] is the last item, whatever the length turns out to be — no need to know how many items there are.

print(labels[-1])   # R-003
print(labels[-2])   # R-002
print(len(labels))   # 3

3.Slicing

Same rule as range(start, stop) — stop is never included.

values = [10, 20, 30, 40, 50]

print(values[1:3])   # [20, 30]
print(values[:2])     # [10, 20]
print(values[2:])     # [30, 40, 50]

4.Mutating and looping

Lists can be changed in place — strings cannot. for loops directly over the values, no counting needed.

values[0] = 99
values.append(60)
values.remove(20)
print(values)

for v in values:
    print(v)

5.Tuples — like a list, but locked

Same () instead of []. Indexing and slicing work exactly the same way — but a tuple cannot be changed after it is created. No .append(), no changing an item.

You have already used one. Week 3's return difference, percent, status sent back a tuple — three values as one — and difference, percent, status = check_record(...) unpacked it into three names.

point = (3, 7)
print(point[0])   # 3 - indexing works the same as a list

# point[0] = 5     # TypeError: 'tuple' object does not support item assignment

6.Strings slice the same way too

You have been indexing and slicing without knowing it since Week 1. A string follows the exact same rules as a list — and like a tuple, it is locked.

record_id = "R-001"

print(record_id[0])      # 'R' - same indexing rule
print(record_id[-1])      # '1' - same negative indexing
print(record_id[0:2])      # 'R-' - same slicing rule, stop excluded
print(record_id[-3:])       # '001'
# record_id[0] = "X"
# TypeError: 'str' object does not support item assignment

Same lock as a tuple — you can read a character, not change one in place. The full toolbox of string methods (.upper(), .strip(), .replace() and more) is coming properly in Week 7. For now: the shape you already know for lists and tuples works on text too.

7.Building a list in one line — list comprehensions

A for loop that builds a new list by appending is common enough that Python has a shorter way to write exactly that.

doubled = []
for v in values:
    doubled.append(v * 2)
print(doubled)

# the same thing, written as a list comprehension
doubled = [v * 2 for v in values]
print(doubled)
[  v * 2   for v in values  ]
     │            │
what to keep   where each v comes from

Add if condition at the end to filter as you build.

big_values = [v for v in values if v >= 50]
print(big_values)

Same idea, three fields

labels[3] when there are only 3 items IndexError: list index out of range the last valid index is len(labels) - 1
values[1:3] expecting 3 items gives 2 stop is never included, same as range()
trying name[0] = "z" on a string TypeError strings cannot be changed this way — lists can
.remove(x) when x is not in the list ValueError check with in first, or catch the error
point[0] = 5 on a tuple TypeError: 'tuple' object does not support item assignment tuples cannot be changed — use a list if you need to

Part 2

Dictionaries

Official docs: Dictionaries

A list finds things by position. A dictionary finds things by name.

Resources

Python documentation — Data Structures: Dictionaries — the official reference, if you want more than this walkthrough covers.

1.Creating and accessing

record = {
    "label": "R-001",
    "value": 87.0,
    "limit": 100.0,
}

print(record["label"])
print(record["value"])
record = { "label": "R-001",  "value": 87.0,  "limit": 100.0 }

record["value"]  ──▶  87.0
record["missing"]  ──▶  KeyError

Animation — Dict Lookup — open this on the main screen to compare list lookup with dict lookup interactively.

2.Adding and updating

The same line does both — if the key exists, it updates; if not, it adds.

record["status"] = "OK"     # new key
record["value"] = 90.0       # existing key, updated
print(record)

3.Missing keys, and .get()

record["missing"] raises KeyError. .get() does not — it gives you None, or a default of your choosing.

print(record.get("status"))          # OK
print(record.get("missing"))          # None
print(record.get("missing", "n/a"))    # n/a

4.Iterating

.items() gives you both the key and the value together — the one you will use most.

for key, value in record.items():
    print(f"{key}: {value}")

5.zip() — building a dict from two lists

Sometimes your data starts as two separate lists — names in one, values in another — instead of already paired up. zip() pairs them together, one from each; dict() turns those pairs straight into a dictionary.

hostnames = ["srv-01", "srv-02", "srv-03"]
disk_used = [87, 45, 120]

paired = list(zip(hostnames, disk_used))
print(paired)     # [('srv-01', 87), ('srv-02', 45), ('srv-03', 120)]

usage = dict(zip(hostnames, disk_used))
print(usage)                  # {'srv-01': 87, 'srv-02': 45, 'srv-03': 120}
print(usage["srv-02"])         # 45
hostnames:   srv-01     srv-02     srv-03
                │          │          │
disk_used:     87         45        120
                │          │          │
zip pairs:  (srv-01,87) (srv-02,45) (srv-03,120)

If the two lists are different lengths, zip() stops at the shorter one — silently, with no error.

5.Sets — only unique values, in curly braces too

Created with {a, b, c} — or set() for an empty one. Not {}: that makes an empty dict, not an empty set. No order, no indexing, and duplicates are dropped automatically.

labels = ["R-001", "R-002", "R-001", "R-003"]
unique_labels = set(labels)

print(unique_labels)          # duplicates gone
print(len(unique_labels))      # 3, not 4
print("R-001" in unique_labels)   # True - fast membership check

empty_set = set()    # NOT {} - that is an empty dict

Same idea, three fields

Field Looks like
AI / Data Science {"rows": 1200, "missing": 13, "source": "survey_2026"}
Cyber Security {"ip": "10.0.0.5", "failed": 12, "locked": True}
IT {"hostname": "srv-01", "used_gb": 87, "total_gb": 120}

Common mistakes

Mistake What you see Fix
record["missing"] KeyError: 'missing' check with .get() or in first
record[value] when you meant record["value"] NameError (or wrong result) keys are strings — quote them
assuming key order matters for lookup it doesn't — lookup is by name, not position that is the entire point of a dict
for value in record: expecting key AND value only gives you the keys use .items() for both
{} expecting an empty set it is an empty dict use set() for an empty set
zip()-ing two lists of different lengths silently stops at the shorter one, no error check both lists are the same length first

Part 3

Files

Official docs: Reading and writing files · open()

Everything so far disappears the moment the program ends. A file does not.

Resources

Python documentation — Reading and Writing Files — the official reference, if you want more than this walkthrough covers.

1.Writing, with with

with ... as f: opens the file, hands you f to work with, and closes it automatically when the indented block ends — even if something goes wrong partway through.

with open("output.txt", "w") as f:
    f.write("R-001\n")
    f.write("R-002\n")
with open("output.txt", "w") as f:
       │
       ▼
  file is open, f is your handle
       │
       ▼
  ... f.write(...) ...
       │
       ▼
  block ends  ──▶  file closes automatically, even if an error happened

2.Reading

No mode given defaults to "r" (read). "w" overwrites the whole file every time you open it that way — "a" appends instead.

with open("output.txt") as f:
    text = f.read()

print(text)

Animation — File Modes — open this on the main screen to show why "w" truncates a file and "a" does not.

3.Reading line by line

Looping over an open file gives you one line at a time — the natural way to process many records. Each line keeps its trailing \n — .strip() removes it.

with open("output.txt") as f:
    for line in f:
        print(line.strip())

4.Splitting a line into fields

.split(",") turns one line of text into a list of values — still text, so convert what needs converting.

line = "R-001,87,100"
label, value, limit = line.split(",")
value = float(value)
limit = float(limit)
print(label, value, limit)

Same idea, three fields

Field Looks like
AI / Data Science loading a CSV of readings before doing anything with it
Cyber Security reading a log file line by line, checking each entry
IT reading a list of hostnames from a config file

Common mistakes

Mistake What you see Fix
opening a file that does not exist FileNotFoundError check the path — is it relative to where you are running from? (or catch it — Topic 4)
forgetting .strip() before comparing or splitting a line odd, hard-to-spot mismatches every line from a file carries a trailing \n
using "w" when you meant "a" your previous content is gone "w" overwrites, "a" appends — pick deliberately
forgetting to convert after .split() TypeError when you try to calculate everything from .split() is still text

Part 4

Handling Errors

Official docs: Errors and exceptions

A file that should be there sometimes isn't. A value that should be a number sometimes isn't. Until now, both have crashed the whole program.

Resources

Python documentation — Errors and Exceptions — the official reference, if you want more than this walkthrough covers.

1.Two failures you already know

Both of these already exist in code you have written. Neither is a bug in Python — Python is doing exactly what it should when it does not know how to continue.

value = int("abc")                 # ValueError — Week 1
with open("missing.txt") as f:     # FileNotFoundError — last topic
    text = f.read()

A crash stops the whole program, right there. Often you already know what should happen instead — a crash never gives you the chance to say so.

# run this once, so section 2 has something real to catch
try:
    int("abc")
except ValueError:
    print("yes — this really does raise ValueError")

2.try / except — catch it, decide what happens next

Python runs the try block. If the named error happens inside it, execution jumps straight to the matching except — the rest of the try block is skipped, but the program does not crash.

try:
    with open("missing.txt") as f:
        text = f.read()
except FileNotFoundError:
    print("missing.txt not found — using an empty report instead")
    text = ""

print(repr(text))     # '' — the program kept going

3.Name the exception you expect

except: on its own catches everything — including a typo in your own code, three lines away, that has nothing to do with the problem you were actually planning for. Name the exception. If more than one thing can go wrong, use more than one except.

def safe_divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        print("can't divide by zero")
        return None
    except TypeError:
        print("both values need to be numbers")
        return None

print(safe_divide(10, 2))      # 5.0
print(safe_divide(10, 0))      # can't divide by zero -> None
print(safe_divide(10, "two"))  # both values need to be numbers -> None
# WATCH OUT — a bare except hides real bugs, it does not fix them
try:
    result = 10 / 0
except:                    # catches EVERYTHING — even a typo you made
    print("something went wrong")   # ...and you will never know what

as e gives you the actual error object, if you want to see the real message rather than writing your own:

try:
    int("abc")
except ValueError as e:
    print("caught it:", e)     # caught it: invalid literal for int() with base 10: 'abc'

Same idea, three fields

A program that crashes on the first bad input is not "correct" — it is just early to quit.

Field Looks like
AI / Data Science except FileNotFoundError: — skip a dataset that hasn't been uploaded yet, keep processing the rest
Cyber Security except ValueError: — skip a malformed log line, keep scanning the rest of the file
IT except FileNotFoundError: — fall back to default settings when a config file is missing

Same shape, three domains: catch it, decide what "carry on" means, keep going.

Common mistakes

Mistake What you see Fix
a bare except: it catches EVERYTHING, including your own typos always name the exception: except ValueError:
catching the wrong exception the error still crashes the program read the traceback's last line — that word IS the exception name to catch
catching an error and doing nothing the program looks like it worked, but the data is just quietly missing at minimum, print what happened — a silent except: pass is the hardest bug to find
putting too much inside one try you can no longer tell which line actually failed keep the try block to just the risky line or two

Part 5

Putting It Together

Official docs: Reading and writing files · Errors and exceptions

This week's tools combine into the shape almost every real program uses.

Resources

Python documentation — Data Structures — the official reference, if you want more than this walkthrough covers.

1.The shape

file (records.txt)                    a list of dicts
  R-001,87,100                          [ {"label": "R-001", "value": 87,  "limit": 100},
  R-002,120,100      ── load_records() →  {"label": "R-002", "value": 120, "limit": 100} ]
                                            └──────────────────┬──────────────────┘
                                                        one dict per record

Build one by hand first, before loading anything from a file.

records = [
    {"label": "R-001", "value": 87.0, "limit": 100.0},
    {"label": "R-002", "value": 120.0, "limit": 100.0},
]

print(records[0]["label"])   # index into the list, then key into the dict

Animation — List of Dicts — open this on the main screen to show a file's lines turning into a list of dicts.

2.Loading it from a file

Topic 3's load_records — the line-reading and splitting you already wrote, now building the list up one dict at a time.

def load_records(path):
    """Read label,value,limit lines from a file and return a list of dicts."""
    records = []
    with open(path) as f:
        for line in f:
            label, value, limit = line.strip().split(",")
            records.append({"label": label, "value": float(value), "limit": float(limit)})
    return records

3.Processing each record

The loop looks the same whether the list came from Topic 1's by-hand version or Topic 3's file — that consistency is the point.

for record in records:
    percent = (record["value"] / record["limit"]) * 100
    status = "OVER LIMIT" if percent >= 100 else "OK"
    print(f"{record['label']}: {status}")

4.Why this shape

This is the shape most real datasets already come in: rows, each with named fields. Week 6's pandas reads a whole file into exactly this shape in one line — what you just built by hand, pandas will hand you ready-made. Knowing the shape first is what makes that useful instead of magic.
